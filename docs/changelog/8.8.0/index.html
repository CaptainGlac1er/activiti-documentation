Version 8.8.0

Released: 2026-02-25

The largest release in this range. The headline features are ephemeral variables (process variables that are not persisted to the event store) and root process instance identifiers exposed on process instances and tasks.

New Features​

  • Ephemeral variables — a new ephemeral property on variable definitions in the process extension JSON. Ephemeral variables participate in execution but are not written to the event store: the event producer sends an empty value for them, update events null out the previous value, and the query service API exposes the ephemeral flag so clients can filter them out. Task variables are exempt from the ephemeral check, and the property also applies to connector variables.
  • Root process instance id — ProcessInstance now carries the id of the root process instance in a call-activity hierarchy (also added to tasks), and the V2 process instance model includes the linked process instance id. Useful for correlating child instances back to the initiating process.
  • Batch process definition lookup — GetProcessDefinitionsPayload supports multiple process definition IDs in a single call, and a new API retrieves the latest versions of process definitions.
  • Process definition query extension — the process definition query can now include non-user-startable processes (previously only user-startable ones were returned by default).
  • JSON Patch variable mapping extensions — the JSON Patch mapping introduced in 8.7.0 now supports arrays (including inner empty arrays), variables inside the patch path field, and replacing array elements.

Bug Fixes​

  • Initiator is now passed into call activity subprocesses (it was previously dropped).
  • Task name and description are truncated to enforce database length limits instead of failing.
  • Pagination is no longer ignored in the process definition search endpoint.
  • Parallel multi-instance tasks: the collection and loopCardinality expressions are evaluated only at task creation, not again when a task is closed.
  • Task names set by task listeners now show up in the interfaces.
  • Corrected the total count when querying historic process instances.
  • Eliminated duplicated events in certain execution paths.
  • Catch-all error boundary events are now processed only after specific error boundaries are exhausted.

Notable Changes​

  • Subprocess termination — support added for terminating subprocesses from the API.
  • Start event subscriptions of previous deployments are disabled — superseded process definition versions no longer react to start events, preventing accidental triggering of old versions.
  • Auto-deployment disabled by default behavior change in deployment handling.
  • Removed the ACT_IDX_IDENT_LNK_TASK index from the schema.
  • Tasks are updated on every TaskListener callback that changes them, keeping query results consistent.
  • ProcessCompletedEvent now includes actor information.
  • Activity-started events are now emitted for async multi-instance tasks.
  • Upgraded to Spring Boot 3.5.x (final 3.5.7) and updated the Jakarta dependencies.

Breaking Changes & Mitigations​

  • Spring Boot 3.5 baseline — the platform moves from Spring Boot 3.3 to 3.5 (final 3.5.7). Mitigation: review the Spring Boot 3.4/3.5 release notes if you pin Spring dependencies yourself.
  • Multi-instance collections evaluated once — for parallel multi-instance loops, the collection and loopCardinality expressions are now evaluated only when the tasks are created, not again when a task is closed (ACTIVITI-5557). Processes whose expressions read mutable state (for example, a list that grows while tasks are completed) will produce a different number of instances. Mitigation: make multi-instance expressions state-independent, or restructure the data flow so the collection is fixed before the loop starts.
  • Catch-all error boundaries processed last — when an error is thrown, specific error boundaries are matched first and the catch-all boundary (empty errorRef) is used only when none match (AAE-39499). Mitigation: re-validate error flows that combine specific and catch-all boundary events.
  • Task name and description truncated — values exceeding the database length limits are now truncated instead of failing to save (AAE-37567). Mitigation: if you relied on the previous failure, add your own validation or shorten the values.
  • More events for consumers — activity-started events are now emitted for async multi-instance tasks, and ProcessCompletedEvent includes actor information. Mitigation: make sure event consumers tolerate the additional events/fields.
  • Deprecated API — GetProcessDefinitionsPayload.getProcessDefinitionId() is deprecated in favor of getProcessDefinitionIds(); it still works in 8.x. Mitigation: migrate to the plural getter.
  • New opt-in behaviors (off by default) — a none deployment mode, and spring.activiti.disable-existing-start-event-subscriptions, which disables start event subscriptions of previous deployments when a new one is deployed. Mitigation: none unless you enable them — read the behavior carefully before turning them on.
  • Schema: Oracle create script — the ACT_IDX_IDENT_LNK_TASK index was removed from the Oracle create script (new installations only; existing databases are not modified).

Use Cases​

Ephemeral variables for data that should not be stored​

Use the ephemeral flag on a variable definition when a variable is needed during execution but should not be exposed in the event store — for example, high-churn intermediate values or data you do not want persisted through the event/audit pipeline:

{
  "id": "order-extensions",
  "extensions": {
    "orderProcess": {
      "properties": {
        "scratch": {
          "name": "scratch",
          "type": "string",
          "required": false,
          "ephemeral": true
        }
      }
    }
  }
}

Variable events for ephemeral variables still fire, but the payload carries an empty value, and VariableCreatedEvent, VariableUpdatedEvent, and VariableDeletedEvent report isEphemeralVariable() as true so consumers can skip persisting them.

Correlating child process instances with the root​

ProcessInstance (and Task) now expose the root process instance id, which is useful for dashboards and logging that must correlate call-activity children back to the initiating process:

import org.activiti.api.process.model.ProcessInstance;
import org.activiti.api.process.runtime.ProcessRuntime;

ProcessInstance instance = processRuntime.processInstance(processInstanceId);
String rootId = instance.getRootProcessInstanceId();

Batch process definition lookup​

GetProcessDefinitionsPayload accepts multiple definition ids and keys in one call, avoiding repeated lookups when rendering lists of processes:

import org.activiti.api.process.model.builders.GetProcessDefinitionsPayloadBuilder;
import org.activiti.api.process.model.payloads.GetProcessDefinitionsPayload;
import org.activiti.api.process.runtime.ProcessRuntime;
import org.activiti.api.runtime.shared.query.Pageable;

GetProcessDefinitionsPayload payload = new GetProcessDefinitionsPayloadBuilder()
    .withProcessDefinitionId("orderProcess:1:abc123")
    .withProcessDefinitionKey("invoiceProcess")
    .withLatestVersionOnly(true)
    .build();

var page = processRuntime.processDefinitions(Pageable.of(0, 20), payload);

JSON Patch mapping of JSON variables​

See the 8.7.0 JSON Patch example for the base syntax. From 8.8.0 on, patch paths also support variables, array indices, and replacing array elements.
